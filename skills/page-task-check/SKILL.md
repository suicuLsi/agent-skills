# 页面任务验收

检查用户能否完成目标任务，以及页面是否如实表达结果。构建通过、截图漂亮、点击有响应，各自都只是局部证据。

## 确认检查对象

确认目标页面、运行版本、身份角色与数据环境。先复用项目已有的运行、检查和浏览器工具；遵守其资源限制，不另起重复服务或测试框架。

从已确认需求提取一条主要任务，选择受此次改动影响的代表性路径与必要边界。没有真实用户任务时，可提出待确认的任务假设；不能用演示数据反推客户业务。

只读审计不修改产品代码、正式记录或权限。验证写操作优先使用已授权的隔离数据，记录测试前状态与恢复办法。需要额外权限的操作标出边界，不把“验收”当作授权。用户已授权实现时继续修复范围内问题，不重新索要同一批准。

## 定义可观察结果

在操作前写清“起点 → 用户判断 → 动作 → 可观察结果”。按当前任务选用检查，下面不是每页必跑的清单。

| 任务 | 验收重点 |
|---|---|
| 比较字段 | 对象身份与同一字段同时可见、固定对齐；数值单位一致，未知不冒充零；排序后仍能确认是哪条记录 |
| 推进阶段 | 鼠标与键盘有等价入口；阶段位置对应正式状态；区分乐观显示、保存中、已确认和失败；必要时刷新核对结果 |
| 筛选与找回 | 搜索／筛选／视图切换后对象集合正确；进入详情再返回、刷新或打开链接时保留约定的上下文 |
| 阅读并编辑详情 | 先能读懂身份、状态与依据；编辑、取消、保存失败和冲突的行为明确，不丢未保存输入 |
| 看图并选择方案 | 预览足够识别对象；选择、采用与正式批准不混淆；能回到选中方案的来源和版本 |
| 讨论与交接 | 能辨认说话人、时间、引用对象和回复关系；当前结论与历史意见不混淆；可定位相关文件或工作页 |
| 复用资源 | 能找到正式版本及其来源，知道在哪些工作中使用；复用不会静默覆盖原件或制造失去关系的副本 |

优先检查改动引入的具体风险。例如：列表改成紧凑布局，需要核对关键比较列在窄屏是否仍可达；纯颜色修改无需因此测试所有业务流转。

## 运行与取证

1. 记录改造前任务路径和代表性页面。截图标记视口、角色、筛选与所用数据；截图中不暴露凭据或不必要的私人信息。
2. 追踪受影响的现有入口、事件处理、权限判断与写入路径。CSS 调整也可能隐藏字段或扩大点击区域，不能只看组件名称。
3. 在实际页面走任务，使用当前可见界面确认下一步。仅源码可用时完成源码检查，并明确交互未验证；不能编造截图或操作结果。
4. 运行项目要求且与修改相称的检查。状态写入要核对真实保存或重新加载结果；前端隐藏按钮不能证明服务器拒绝越权。
5. 在可比较的视口、角色和数据下记录修改后结果。对有状态页面解释必要的前后差异；在授权范围内恢复隔离测试数据与临时视口设置。

失败测试、多人冲突、权限或网络模拟只在相关且有安全验证手段时执行。无法验证就说明缺口，不在生产中人为制造故障，也不因为无法模拟就宣布通过。

## 结论要求

每个发现写明：**发生位置与条件 → 实际观察 → 对任务的影响 → 最小修复或待验证项**。不要只有“层级混乱”“体验不好”。

对每条任务区分已验证、失败、未验证；附相关命令结果、截图或页面证据。把以下边界写清：

- 源码判断与浏览器实测；
- 乐观反馈与持久化结果；
- 隔离数据与真实协作环境；
- 技术检查通过与客户实际可用性。

找不到对照数据、销售口径或业务审批规则时，保留为人工判断，不能用占位值补齐后宣称流程成立。关于更快、更省时的结论需要实际观察或测量，不能只由像素或点击数推出。

简单任务用简短结果即可；较大改造交付“任务｜结果｜证据｜剩余问题”表及代表性的前后截图。验证完成后不继续扩展无关审计。

## 范围

任务尚未明确时，先确认用户、业务对象和目标结果。信息位置影响任务时，记录具体位置和后果。只有几何偏差、配色或性能问题时，按该问题单独检查。

自检反例：按钮点击后换了列但保存失败，不能判流转通过；只有构建结果，交互结论应为未验证；只获得“先审计”授权，不因发现问题就修改页面。

可以用[订单状态示例](examples/order-status.md)练习如何判断界面反馈与保存结果不一致的情况。
